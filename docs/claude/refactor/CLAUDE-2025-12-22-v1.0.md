# 玩家標籤資料同步優化系統 v2.0

## 完成狀態
🚧 **規劃階段** (2025-12-22)

## 功能概述
基於 fat-identity-cat 專案的標籤同步優化方案，對 fat-notification-cat 的標籤批次更新功能進行效能優化，透過快取機制與資料比對減少無效的 DB I/O 開銷。

## 問題分析

### 當前架構現況
**fat-notification-cat** 已具備相當優化的玩家標籤同步架構：
- ✅ **v1.5 已實現**: UseCase層差異計算 + Repository層精確操作的分離設計
- ✅ **v1.5 已實現**: `QueryWithCache` 泛型快取查詢函數 (`utils/QueryWithCache`)
- ✅ **v1.5 已實現**: `BatchUpdateWithDiff` 精確差異更新介面
- ✅ **v1.5 已實現**: 快取命中時0次資料庫查詢，無變化時0次資料庫寫入
- ✅ **Clean Architecture**: UseCase處理業務邏輯和快取管理，Repository專注資料庫操作

### 待優化區域
**位置**: `internal/application/usecase/player/player_tag_usecase.go:112`

**目前實作**:
```go
// 更新或創建Tags - 待優化區域
if err = u.tagRepo.BatchUpsert(ctx, tagsToInsert); err != nil {
    return fmt.Errorf("batch upsert tags failed: %w", err)
}
```

**問題**:
- 對所有標籤執行 BatchUpsert，無論是否真的需要更新
- 未使用快取預檢查機制減少資料庫操作
- 缺乏智能比較邏輯過濾不需要更新的標籤

## 技術實作規劃

### 解決方案
參考 identity 專案的快取感知批次更新機制，在 UseCase 層實作快取預檢查，透過 Redis 快取預先比較標籤變動，只對真正需要更新的標籤執行資料庫操作。

### 核心優化功能設計

#### 1. UseCase 層快取邏輯強化
**目標位置**: `internal/application/usecase/player/player_tag_usecase.go:112`

**新增功能特性**:
- 🔍 **快取預檢查**: 在 UseCase 層使用 Redis 快取檢查標籤是否存在及最後更新時間
- 🔄 **智能比較**: 比較 name、updated_at、deleted_at 等欄位判斷是否需要更新
- ⚡ **只更新必要的標籤**: 過濾掉不需要更新的標籤，大幅減少資料庫操作
- 🚀 **非同步快取更新**: 更新後自動更新快取，不影響主流程效能
- 🏗️ **Clean Architecture 合規**: 擴展現有架構，保持快取邏輯在業務邏輯層

#### 2. 快取設計規格
**快取鍵格式**: `tag:global_id:{global_tag_id}`  
**快取過期時間**: 5分鐘  
**快取內容**: Tag 實體完整資訊（JSON序列化）

**Redis 操作策略**:
- **寫入策略**: Write-Through (更新資料庫後同步更新快取)
- **批次優化**: 使用現有 Pipeline 能力進行批次 SET/DEL 操作
- **即時清除**: 單一標籤更新後立即清除對應快取確保一致性

#### 3. 新增 UseCase 層方法
**位置**: `internal/application/usecase/player/player_tag_usecase.go`

**需要新增的核心方法**:

**Redis 快取支援**:

### 使用方式對比

#### 優化前（當前實作）
```go
// 直接批次更新所有標籤，無快取預檢
if err = u.tagRepo.BatchUpsert(ctx, tagsToInsert); err != nil {
    return fmt.Errorf("batch upsert tags failed: %w", err)
}
```

#### 優化後（目標實作）
```go
// 1. 使用快取篩選需要更新的標籤
tagsToUpsert, err := u.filterTagsNeedingUpdate(ctx, tagsToInsert)
if err != nil {
    return fmt.Errorf("filter tags needing update failed: %w", err)
}

// 2. 只對需要更新的標籤執行資料庫操作
if len(tagsToUpsert) > 0 {
    if err = u.tagRepo.BatchUpsert(ctx, tagsToUpsert); err != nil {
        return fmt.Errorf("batch upsert tags failed: %w", err)
    }
    // 3. 非同步更新快取
    go u.updateTagCache(context.Background(), tagsToUpsert)
}
```

### 效能預期改善

#### 資料庫負載減少
- **預期減少**: 60-80% 的不必要 INSERT/UPDATE 操作
- **快取命中且無變化**: 0次資料庫操作（基於現有 v1.5 架構優勢）
- **快取命中有變化**: 只操作真正變動的標籤

#### 回退機制保證
- **快取不可用時**: 自動回退至原始 `BatchUpsert()` 方法
- **快取錯誤處理**: 快取讀取失敗時假設需要更新，確保資料一致性  
- **零風險**: 不會因快取問題造成資料遺失

#### 快取策略
- **寫入策略**: Write-Through (更新資料庫後同步更新快取)
- **批次優化**: 使用現有 Redis Pipeline 進行批次 SET/DEL 操作
- **即時清除**: 單一標籤更新後立即清除對應快取確保一致性
- **失效策略**: 提供手動清除快取方法
- **容錯設計**: 快取操作失敗不影響核心業務流程

### 架構優勢延續

1. **Clean Architecture 合規**: 
   - 擴展現有 v1.5 UseCase 層設計
   - Repository 層保持純資料存取職責
   - Infrastructure 層處理快取實作細節

2. **正確的關注點分離**: 
   - Repository: 純資料存取，無業務邏輯
   - UseCase: 業務邏輯 + 快取策略 + 差異計算
   - Infrastructure: 快取與分佈式鎖實作

3. **向後相容**: 
   - 保留原有 `BatchUpsert()` 方法
   - 不影響現有功能
   - 漸進式優化策略

4. **測試友善**: 
   - UseCase 可注入 Mock CacheManager 進行單元測試
   - 基於現有測試架構擴展

5. **維護性**: 
   - 快取邏輯集中在業務層
   - 易於理解和維護
   - 基於現有架構模式

6. **擴展性**: 
   - 快取模式可應用到其他 UseCase
   - 無需修改 Repository 層

### 風險評估與緩解

#### 風險識別
1. **快取一致性風險**: Redis 快取與 MySQL 資料不一致
2. **記憶體使用增加**: Tag 實體快取消耗 Redis 記憶體
3. **複雜度提升**: 快取邏輯增加系統複雜度

#### 緩解策略
1. **一致性保證**:
   - 使用 Write-Through 策略
   - 短期快取過期時間（5分鐘）
   - 失敗時自動回退到無快取模式

2. **記憶體管理**:
   - 短期 TTL 自動過期清理
   - 監控 Redis 記憶體使用量
   - 必要時可調整快取策略

3. **複雜度控制**:
   - 基於現有架構擴展
   - 完善的單元測試覆蓋
   - 清晰的錯誤處理機制

## 結論

本優化方案基於 fat-notification-cat 現有的優秀架構基礎（v1.5），參考 fat-identity-cat 的成功實作經驗，針對 Tag 批次更新的特定瓶頸進行精確優化。通過快取預檢查機制，預期可將 Tag 批次更新的無效操作減少 60-80%，進一步提升系統整體效能。

優化策略著重在**增量改善**而非架構重構，確保在享受性能提升的同時，維持系統的穩定性與可維護性。整個實作過程預計需要 4 個工作天，風險可控，並提供完整的回退機制保證生產環境安全。
