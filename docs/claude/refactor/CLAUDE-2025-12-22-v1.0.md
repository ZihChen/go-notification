### 待優化區域
**位置**: `internal/application/usecase/player/player_tag_usecase.go:112`

**目前實作**:
```go
// 更新或創建Tags - 待優化區域
if err = u.tagRepo.BatchUpsert(ctx, tagsToInsert); err != nil {
    return fmt.Errorf("batch upsert tags failed: %w", err)

```

**問題**:
- 對所有標籤執行 BatchUpsert，無論是否真的需要更新
- 未使用快取預檢查機制減少資料庫操作
- 缺乏智能比較邏輯過濾不需要更新的標籤

## 技術實作規劃

### 解決方案
參考 identity 專案的快取感知批次更新機制，在 UseCase 層實作快取預檢查，透過 Redis 快取預先比較標籤變動，只對真正需要更新的標籤執行資料庫操作。

### 核心優化功能設計

#### 1. UseCase 層快取邏輯強化
**目標位置**: `internal/application/usecase/player/player_tag_usecase.go:112`

**新增功能特性**:
- 🔍 **快取預檢查**: 在 UseCase 層使用 Redis 快取檢查標籤是否存在及最後更新時間
- 🔄 **智能比較**: 比較 name、updated_at、deleted_at 等欄位判斷是否需要更新
- ⚡ **只更新必要的標籤**: 過濾掉不需要更新的標籤，大幅減少資料庫操作
- 🚀 **非同步快取更新**: 更新後自動更新快取，不影響主流程效能
- 🏗️ **Clean Architecture 合規**: 擴展現有架構，保持快取邏輯在業務邏輯層

#### 2. 快取設計規格
**快取鍵格式**: `tag:global_id:{global_tag_id}`  
**快取過期時間**: 5分鐘  
**快取內容**: Tag 實體完整資訊（JSON序列化）

**Redis 操作策略**:
- **寫入策略**: Write-Through (更新資料庫後同步更新快取)
- **批次優化**: 使用現有 Pipeline 能力進行批次 SET/DEL 操作
- **即時清除**: 單一標籤更新後立即清除對應快取確保一致性

**位置**: `internal/application/usecase/player/player_tag_usecase.go`

// 直接批次更新所有標籤，無快取預檢

        return fmt.Errorf("batch upsert tags failed: %w", err)
    }
    // 3. 非同步更新快取
    go u.updateTagCache(context.Background(), tagsToUpsert)

### 效能預期改善

#### 資料庫負載減少
- **預期減少**: 60-80% 的不必要 INSERT/UPDATE 操作
- **快取命中且無變化**: 0次資料庫操作（基於現有 v1.5 架構優勢）
- **快取命中有變化**: 只操作真正變動的標籤

#### 回退機制保證
- **快取不可用時**: 自動回退至原始 `BatchUpsert()` 方法
- **快取錯誤處理**: 快取讀取失敗時假設需要更新，確保資料一致性  
- **零風險**: 不會因快取問題造成資料遺失

#### 快取策略
- **寫入策略**: Write-Through (更新資料庫後同步更新快取)
- **批次優化**: 使用現有 Redis Pipeline 進行批次 SET/DEL 操作
- **即時清除**: 單一標籤更新後立即清除對應快取確保一致性
- **失效策略**: 提供手動清除快取方法
- **容錯設計**: 快取操作失敗不影響核心業務流程

3. **複雜度提升**: 快取邏輯增加系統複雜度

#### 緩解策略
1. **一致性保證**:
   - 使用 Write-Through 策略
   - 短期快取過期時間（5分鐘）
   - 失敗時自動回退到無快取模式

2. **記憶體管理**:
   - 短期 TTL 自動過期清理
   - 監控 Redis 記憶體使用量
   - 必要時可調整快取策略

3. **複雜度控制**:
