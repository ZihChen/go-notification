## 問題一：go-test job 失敗（exit code 1）

### 現象
`go-test` job 回報 exit code 1，但所有測試實際上都有通過。

### 根本原因（第一層）
Cache 路徑使用絕對路徑（`/go/pkg/mod`、`/root/.cache/go-build`），這些路徑在 project directory 之外，GitLab Runner 無法快取，導致 runner 警告並影響 job 結果。

### 根本原因（第二層，真正原因）
修完 cache 路徑後，新的 CI log 才顯示真正錯誤：  
上傳 `coverage.xml`（36,781 行）到 GitLab 作為 Cobertura report artifact 時，GitLab 回傳 **500 Internal Server Error**，檔案太大超出限制。

### 解法
1. 將所有 cache 路徑改為 project 相對路徑，並設定 `GOPATH`、`GOCACHE`、`GOBIN` 環境變數指向 `.cache/` 目錄
2. 移除 `gocover-cobertura` 的安裝與執行，移除 `artifacts.reports.coverage_report` 區塊
3. 保留 `coverage:` regex，GitLab 仍可從 stdout 擷取覆蓋率百分比

### 相關 commits
- `4937089` fix(ci): move cache paths inside project directory
- `856ce18` fix(ci): remove cobertura artifact upload causing 500 error

### 狀態
✅ **已解決**

## 問題二：build job 失敗（ECR 401 Unauthorized）

### 現象
`build` job 失敗，log 顯示：
```
unauthorized: authentication required
```

### 根本原因
`macmini-designer` runner 使用 Docker executor，**不支援 privileged mode**，所有需要 DinD（Docker-in-Docker）的方案都無法使用。

### 解法嘗試過程

#### 嘗試一：docker:dind + aws-cli（失敗）
**結果：** `FATAL: No HOST or PORT found` — DinD 無法運行。  
Commit: `5dbd32e`

#### 嘗試二：kaniko + 下載 aws-cli v2 binary（失敗，/tmp 不存在）
**結果：** `wget: can't open '/tmp/awscliv2.zip': No such file or directory`  
Commit: `45421af`

#### 嘗試三：加上 mkdir /tmp（失敗，glibc 缺失）
**結果：** aws-cli v2 是 glibc binary，kaniko:debug 是 distroless 容器，無法執行。  
Commit: `bb6afa4`

#### 嘗試四：分離 ecr-auth job + dotenv artifact（失敗，AWS 憑證未設）
架構：Alpine 取得 ECR token → dotenv artifact → kaniko 讀取  
**結果：** GitLab CI/CD Variables 未設定，`Unable to locate credentials`  
Commit: `3564400`

#### 嘗試五：設定 AWS key 後，dotenv artifact 500 問題
DevOps 設定 `qcatDevCicd` 的 `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` 後，  
ECR token 取得成功，但 GitLab **dotenv artifact 上傳回 500**（token 值太長，超出 dotenv 變數大小限制）。  
Commit: `08cbad7`

#### 嘗試六：改用 file artifact 傳遞 config.json（失敗，file artifact 也 500）
**結果：** GitLab 這個 self-hosted instance 對所有 artifact 上傳都有問題（500 Internal Server Error），不管是 dotenv 還是一般檔案。  
Commit: `73de6a5`

#### 最終方案：使用 kaniko 內建 ECR credential helper（成功）
kaniko `debug` image 內建 `docker-credential-ecr-login`，只需要設定環境變數即可自動認證 ECR，完全不需要額外的 auth job，也不需要傳遞任何 artifact。

**所需 GitLab CI/CD Variables：**
- `AWS_ACCESS_KEY_ID`（已設定）
- `AWS_SECRET_ACCESS_KEY`（已設定）
- `AWS_DEFAULT_REGION`（job variables 設定）

Commit: `2c1b42d`

### 狀態
✅ **已解決**

## 問題三：build job 推送三個獨立 image（優化）

### 現象
原本設計 `build-dev`、`build-latest`、`build-commit-sha` 三個 job 各 build 一次，各推一個 tag，浪費時間與資源。

### 解法
使用 kaniko 多 `--destination` 支援，**一次 build 同時打兩個 tag**：`:latest` 和 `:{CI_COMMIT_SHA}`，移除 `:dev` tag（語意不明確）。

Commit: `8a82351`

### 狀態
✅ **已完成**

## 最終 Pipeline 架構

```
MR 開啟中：    ai-review → lint-check → go-test
push/merge dev：ai-review → lint-check → go-test → build → deploy-dev
```

| Job | 觸發條件 |
|---|---|
| ai-review | MR / push to dev |
| lint-check | MR / push to dev |
| go-test | MR / push to dev |
| build | push to dev only |
| deploy-dev | push to dev only |

### build job 行為
- 一次 build，推送兩個 tag：`:latest`、`:{full-commit-sha}`
- 使用 kaniko 內建 ECR credential helper，零 artifact 傳遞
